# 錢脈

> 更新於 2026-10-01：PC 本機版已具備聯絡人、聯絡追蹤、紀錄計分及週／月報。完整行程與後台仍在補齊，手機測試暫緩；最新狀態見第二十五節。

## 啟動 PC 預覽

在專案終端執行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\dev.ps1
```

開啟 http://localhost:8081 。先建立測試帳號或使用 seed 帳號登入，即可新增／編輯／搜尋聯絡人、填寫生日及新增自訂等級。資料存於本機 API 的 SQLite，請使用假資料測試。

其他電腦需先安裝 Node.js 24 LTS，執行 `npm ci`、`npm run dev`。詳細結構、已完成與未完成範圍見 [實作架構](docs/architecture.md)，驗證結果見 [測試紀錄](docs/testing.md)。

**錢脈**是一款以**行事曆**為核心，整合聯絡人管理、客戶追蹤、未定行程與業務計分的業務管理 App。

產品主要面向台灣業務人員，希望透過簡單直覺的操作方式，協助使用者管理人脈、安排業務行程、維持客戶聯絡頻率，並透過適度的遊戲化設計，提高持續使用與完成業務目標的動力。

# 一、專案背景

保險業務人員在日常工作中，需要持續管理大量客戶、潛在客戶與業務行程。

常見需求包含：

* 管理聯絡人
* 記錄客戶資訊
* 管理客戶重要程度
* 維持固定聯絡頻率
* 記錄與客戶的互動
* 安排下一次聯絡
* 管理每日行程
* 保存尚未確定日期的事項
* 追蹤每日或週期性的業務目標

目前市面上已有相關業務管理工具，但部分產品功能較多、操作較複雜，並非所有功能都符合實際業務工作的需求。

因此，本專案希望建立一套：

> **簡單、快速、以行事曆與人脈管理為核心的業務管理工具。**

# 二、產品核心概念

錢脈並非單純的聯絡人 App，也不是單純的行事曆。

目前產品核心由四個主要功能組成：

```text
錢脈
│
├── 行事曆
│
├── 新增聯絡人(可能使用+符號)
│
├── 聯絡人管理
│
├── 未定行程
│
└── 計分卡
```

使用者開啟 App 後，主要透過行事曆掌握每日工作，再從聯絡人、未定行程與計分系統完成日常業務管理。

行事曆主要負責：

## 6.2 月曆顯示

目前已接上聯絡人的首次與下次聯絡安排，日期顯示筆數，下方列出當日行程；獨立多筆自由行程仍待實作。

# 八、客戶分級

已確認預設等級與聯絡間隔：

| 等級 | 聯絡間隔 |
| --- | --- |
| A | 1 週 |
| B | 1 個月 |
| C | 3 個月 |

A、B、C 的聯絡間隔固定，使用者不可修改。使用者可自行新增自訂名稱等級，並設定各自的聯絡間隔。月份暫按日曆月計算，月底無對應日期時取該月最後一天；計算細節與預設等級規則見 [需求規格](docs/requirements.md)。

# 九、聯絡頻率

客戶等級將與聯絡頻率產生關聯。

例如：

```text
王先生
│
├── 等級：A
│
├── 上次聯絡：2026/09/07
│
└── 聯絡頻率：1 週

        ↓

```

當使用者完成一次聯絡後，系統可以依照客戶等級與聯絡頻率，產生下一次建議聯絡日期。

目前傾向：

> **系統自動提供建議日期，但使用者仍可以自行調整。**

實際規則尚待確認。

# 十一、未定行程

「未定行程」為獨立於主要行事曆之外的功能入口。

其目的為保存：

> **知道需要處理，但目前尚未確定正式日期或時間的事項。**

避免事情因為沒有排入正式日曆而被遺忘。

---

## 11.1 未定行程來源

目前可能包含兩種類型。

### 1. 尚未確定日期

例如：

```text
張先生

事項：
安排時間討論醫療險。

日期：
未定

原因：
等待客戶確認時間。
```

### 2. 原定行程未完成

例如：

```text
王先生

原定日期：
2026/09/06

事項：
例行聯絡

狀態：
尚未完成
```

如果原定行程已經過期但尚未完成，可以進入未定行程，等待重新安排。

原始日期應保留，以保存行程歷史。

---

## 11.2 未定行程介面

採用類似日曆的方式呈現。

但：

> **主要行事曆與未定行程為兩個不同入口。**

使用者可以點擊未定行程中的項目查看詳細資訊。

詳細 UI 與排序方式尚待設計。

---

## 11.3 重新安排

未定行程確認正式日期後：

```text
未定行程
    ↓
選擇日期 / 時間
    ↓
正式排程
    ↓
進入主要行事曆
```

# 十二、計分卡

錢脈預計加入業務 KPI / 計分系統。

不同業務行動可以獲得不同分數。

概念例如：

```text
聯絡客戶       + N 分
與客戶吃飯     + N 分
完成拜訪       + N 分
完成指定行動   + N 分
```

目前採用下列六項計分規則；分數由後端提供，保存紀錄時保留當時分數。

---

## 12.1 計分規則

計分規則由後台統一設定且可調整

例如：

```text
管理後台

聯繫          1 分
接觸          5 分
活動          5 分
看店          8 分
深度面談      10 分
上卡         40 分
```

修改規則後，App 可以取得最新計分設定。

如此可避免每次調整 KPI 都需要重新發布 App。

---

# 十三、成果回饋與使用動力

採用溫暖綠金配色、每日成果摘要與清楚的操作回饋，不做角色養成或遊戲系統。每日得分與跨日總分無上限，不設定 40 分滿分或達標進度。

計分卡只能查詢，聯絡紀錄選擇計分項目並儲存後才計分；刪除紀錄會撤銷分數。後台可決定週報或月報，結算不清除累計總分。

# 十五、資料授權

目前需求包含使用者之間的資料授權機制。

例如：

```text
使用者 A
    │
    │ 授權
    ↓
使用者 B
```

授權後：

```text
B 可以查看 A 的資料
B 不可以修改 A 的資料
後台管理帳號可以修改
```

因此權限概念至少包含：

```text
自己的資料
├── 查看
├── 新增
├── 修改
└── 刪除

被授權的其他使用者資料
├── 查看
└── 不可修改
```

* 可以取消授權
* 需要授權紀錄

```text

                      │

            │                   │
        Mobile App          管理後台
            │                   │
            └─────────┬─────────┘
                      │
                    Backend
                      │
                   Database
```

主要負責：

* 一般使用者權限管理
* KPI / 計分規則設定


後台帳號可直接查看所有使用者的：

* 聯絡人
* 行程
* 聯絡紀錄
* KPI

此項涉及使用者隱私與客戶個人資料，正式開發前必須明確定義。

# 十九、資料安全與隱私

錢脈預期可能處理：

* 姓名
* 電話
* Email
* 生日（及保留的舊版重要日期）
* 聯絡紀錄
* 人際關係資訊
* 客戶分類
* 行程
* 業務備註
* KPI 資訊

因此資料安全屬於核心需求。

基本原則：

* 使用者必須經過身分驗證
* 不同使用者資料必須隔離
* 資料存取必須經過權限檢查
* 被授權資料應遵守 Read-only 等權限限制
* 客戶資料不得公開存取
* 測試期間不得任意使用真實客戶資料
* 正式環境與開發環境應適當區隔
* 敏感資訊不得直接寫入程式碼
* Backend 必須實作正式授權機制

正式上線前，應另外確認台灣個人資料保護及相關法規要求。

# 二十三、開發流程與兩個月交付目標

目標為 **60 個日曆天完成可供內部試用的 MVP**，包含 iOS／Android 測試版、基本管理後台、驗收紀錄與操作／部署文件。

排程先以 **1 位主要開發者、平均每日約 3 小時（每週約 21 小時）** 估算，適合分散於下班或空閒時間進行。Day 1 為實際開工日，60 天包含週末；可依當週時間安排休息，再將工作移至其他有空的日子，不要求每天固定投入。若每週可投入時間持續低於估算，需縮減範圍或順延日期。商店送審與正式上架另外追蹤，外部審核完成日不列為第 60 天的保證交付。

## 23.3 每日工作方式

1. 確認當日交付物，拆成能在當天驗收的小任務。
2. 從 `develop` 建立 `feature/*` 或 `fix/*`，完成介面與資料串接。
3. 檢查正常操作、空資料、輸入錯誤、失敗提示與權限；關鍵規則補自動化測試。
4. 通過檢查後提交並整合，更新排程、阻礙與下一步。
5. 新需求先記入待辦；若納入本期，同時調整範圍或工期。

已確認採用 **PC 瀏覽器為主要確認方式；手機測試目前暫緩，先補齊 PC 功能**。技術選型必須支援 PC 預覽；手機階段檢查觸控、鍵盤、返回與版面差異，交付前完整驗證 Android 與 iOS。各功能檢查點見 [需求規格](docs/requirements.md)，第一個功能的操作情境見 [使用流程](docs/user-flow.md)。
