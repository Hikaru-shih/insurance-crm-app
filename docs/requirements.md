## 2026-09-22 定稿方向與目前狀態

依使用者「以最新 README 為主」的指示，採最新欄位清單：姓名、性別、IG、群組、備註、生日；只有姓名必填。恢復獨立生日欄位，舊暱稱／手機／Email／重要日期從操作介面移除，但原資料保留。下列規則作為本期實作基準，後續變更須同步驗收條件。

已實作：本機後端、登入／登出、帳號隔離、新版聯絡人及分級、唯讀授權／撤銷 API 與管理員修改 API。管理後台目前僅帳號與操作紀錄骨架。行程、聯絡紀錄、計分卡與完整分享 UI 尚未實作。

目標使用者為台灣業務人員。月曆文字採每筆行程的自訂標題，顏色／顯示上限見 wireframes.md；管理員可修改其他使用者業務資料並留紀錄，一般被授權者仍唯讀。測試帳號可在開發模式註冊，正式邀請及找回帳號流程另列發布待辦。

## 1. 交付目標與範圍

開工日為 2026-09-08，Day 60 暫定為 2026-11-06，以可內部試用的 iOS／Android MVP、基本管理後台及交付文件為目標。依每週實際投入時間調整；商店正式上架另行追蹤。

核心情境：業務新增客戶 → 設定等級 → 安排行程 → 完成聯絡並記錄 → 查看積分 → 確認下一次聯絡。尚未確定日期或逾期未完成的事項可從未定行程重新安排。

| ID | 本版功能 | 最低驗收條件 |
| --- | --- | --- |
| AUTH-01 | 登入、登出、資料隔離 | A、B 登入後各自看到自己的資料；B 未經授權直接請求 A 的資料也被拒絕；登出後受保護資料不可繼續存取 |
| CONTACT-01 | 聯絡人新增、詳情、編輯、刪除 | 可建立並重新讀回資料；修改後保存；刪除須確認，關聯資料依 Day 3–4 定稿規則處理 |
| CONTACT-02 | 搜尋與群組 | 可按姓名、IG 或群組找到客戶；無結果顯示提示；群組以多標籤分類 |
| LEVEL-01 | 自訂等級與聯絡間隔 | A＝1 週、B＝1 個月、C＝3 個月固定不可修改，介面與 Backend 均拒絕使用者更改其間隔；可新增自訂名稱等級並設定間隔數值與單位；套用至客戶後保存；未分級也可建立客戶 |
| CAL-01 | 月曆、當日列表與行程操作 | 月格顯示文字與顏色；選日期可看完整列表；新增、編輯、完成後正確反映於畫面 |
| PENDING-01 | 未定與逾期事項 | 無日期及逾期未完成事項皆可找到；完成事項不誤列；重排保留原始日期，不重複建立事項 |
| LOG-01 | 聯絡紀錄與下次聯絡 | 可讀取歷史互動；有等級間隔時提供建議日期，可手動調整並確認建立下次行程 |
| SCORE-01 | 行動計分與每日計分卡 | 完成指定行動後計分；重複送出不重複加分；依定稿規則撤銷及彙總每日分數 |
| GOAL-01 | 每日目標與回饋 | 顯示今日分數／目標及完成回饋；超過目標仍顯示實際分數 |
| SHARE-01 | 唯讀授權與撤銷 | B 可看 A 授權資料但不可改；撤銷後新請求被拒絕，畫面移除已載入的授權資料 |
| ADMIN-01 | 後台使用者及權限管理 | 管理員可執行允許的管理操作；一般帳號無法呼叫管理 API |
| ADMIN-02 | 業務資料查閱與 KPI 設定 | 可按使用者查閱資料；調整分數後 App 可取得新規則；管理操作留時間、操作者及對象紀錄 |

本期暫不包含：通訊錄同步、批次匯入、週視圖、拖曳排程、推播、排行榜、複雜報表、Streak／徽章／成就、多層級及欄位級授權。這些延續 README 的後續版本安排；若升為本版必要項目，需一起重估工期。

## 1.1 開發預覽與驗證方式（已確認）

日常以 PC 瀏覽器確認畫面、欄位與操作流程；每完成一個完整功能，再使用手機驗證。交付前須完成 Android 與 iOS 的完整流程測試。技術選型必須支援 PC 瀏覽器預覽，使用與 App 共用的業務規則與 Backend，避免另做一套無法驗證 App 邏輯的展示頁。

PC 預覽作為開發驗收工具，本次確認不代表新增正式桌面版產品。手機階段需檢查觸控、鍵盤、返回、版面及平台差異；PC 通過不等同手機驗收通過。

| 功能檢查點 | PC 先確認 | 手機接續確認 |
| --- | --- | --- |
| 登入與聯絡人 | 登入、新增僅姓名的客戶、編輯、搜尋及重新讀取 | 鍵盤不遮住欄位與儲存鈕，返回及資料保存正常 |
| 行事曆與未定行程 | 日期切換、行程詳情、完成、逾期與重排 | 月格文字可讀、點選日期與詳情順暢 |
| 聯絡追蹤與計分 | 紀錄、建議日期、確認排程及分數 | 完整操作順暢，重複點擊不重複寫入 |
| 分享與整合 | 雙帳號唯讀與撤銷、完整流程 | 撤銷後畫面同步移除資料；Android／iOS 均驗證 |

## 2. 聯絡人欄位（D-01，依最新 README）

| 欄位 | 必填／規則 |
| --- | --- |
| 姓名 | 必填，不接受純空白；允許同名 |
| 性別 | 選填，自由文字 |
| IG | 選填，可填帳號或個人頁網址 |
| 群組 | 選填，多個標籤以頓號或逗號分隔，儲存時去空白與重複 |
| 備註 | 選填，多行文字 |
| 生日 | 選填，完整 YYYY-MM-DD、有效且不可為未來日期 |
| 客戶等級 | 獨立業務設定，選填；A／B／C 固定，其餘可自訂 |

舊欄位 nickname／phone／email／importantDates 保留於資料層，不再提供編輯／搜尋。既有日期不自行推定為生日，避免誤轉換。舊瀏覽器資料須使用者明確匯入空白帳號，原資料不刪除。

CONTACT-03 驗收：只填姓名可新增；可保存 IG、性別、群組、備註及生日，重新登入仍可讀回；生日錯誤須提示並保留輸入；舊欄位無操作入口但遷移不丟失資料。

## 3. 分級與聯絡頻率（D-02，預設已確認）

已確認（2026-09-10）：新帳號提供以下預設等級，A、B、C 的聯絡間隔固定，使用者不可修改；使用者可以新增自訂名稱等級並自行設定聯絡間隔。

| 等級 | 預設聯絡間隔 |
| --- | --- |
| A | 1 週 |
| B | 1 個月 |
| C | 3 個月 |
| 自訂名稱等級 | 使用者自行新增並設定 |

計算方式暫採日曆週／月：1 週為 7 天，1 個月或 3 個月按日曆月相加，不固定換算為 30／90 天。目標月份無相同日期時取該月最後一天。自訂間隔提案使用正整數搭配「天／週／月」單位；同一使用者的等級名稱不可重複（去除首尾空白、英文字母統一大寫，限 1–20 字元，可包含中文或數字）。上述計算細節及既有 A／B／C 是否可刪除，仍屬待定細節；使用者不可修改 A／B／C 間隔已確認。

* 建議日期 = 實際聯絡日期 + 該客戶等級的間隔（數值與單位），不以輸入紀錄當天代替實際聯絡日。
* 無等級或尚無聯絡紀錄時，不憑空推算日期，由使用者手動安排。
* 建議日期需使用者確認才建立行程；可以改日期或暫不安排。
* 調整等級或頻率不自動搬動已確認的行程，之後的新建議使用新設定。
* 驗收例：2026/9/10 聯絡，A 建議 9/17、B 建議 10/10、C 建議 12/10；手動改日期並確認後，只產生一筆新行程。月底計算草案：2026/1/31 加 1 個月為 2/28，2028/1/31 加 1 個月為 2/29。

## 4. 行程與聯絡紀錄提案

行程標題必填，關聯客戶選填，以支援公司會議等非客戶事項；日期可空白，時間可空白。有日期無時間視為當日事項。完成狀態、日期與計分行動分開保存，顏色不決定是否完成或如何加分。

聯絡紀錄提案必填：客戶、實際聯絡日期、聯絡方式、內容；選填：備註、下一步、下次聯絡日期。建立聯絡紀錄與完成同一行程不能造成重複計分。

Day 3–4 定稿：逾期判定時間、完成／撤銷完成、刪除關聯、重排歷史與補登行為。Day 5–6 決定月格文字上限、顏色數量與未定行程版型。

後台統一管理行動名稱與分數。依 2026-09-22 使用者更新的 README，採以下六項作為新版規格基準；計分流程尚未實作：

| 行動 | 分數 |
| --- | --- |
| 聯繫 | 1 |
| 接觸 | 5 |
| 活動 | 5 |
| 看店 | 8 |
| 深度面談 | 10 |
| 上卡 | 40 |

* 本期基準每日目標 40 分，由管理員設定全體預設目標；個別目標列為後續擴充。
* 每筆完成行程至多選一種計分行動；不屬於計分項目的行程可完成但不加分。
* 保存完成時的分數，後台改規則只影響後續完成的行動，不回算歷史。
* 撤銷完成撤回原分數；重送相同完成操作不再次加分。重新完成、補登及跨日歸屬於 Day 3–4 明確定義，Day 31–32 驗證模型。
* 日統計使用 Asia/Taipei；日期邊界需在雙平台測試。

## 6. 管理員與分享範圍提案（D-04，待確認）

README 已規劃管理員查閱所有使用者的聯絡人、行程、紀錄及 KPI。本節將可見與可修改分開，避免「最高權限」成為未定義的行為。

| 操作 | 本人 | 被指定授權者 | 管理員 |
| --- | --- | --- | --- |
| 查看聯絡人／行程／紀錄／KPI | 可以 | 授權有效時可以 | 可以查看所有使用者 |
| 修改個人業務資料 | 可以 | 不可以 | 可以，須保存管理操作紀錄 |
| 新增／刪除個人業務資料 | 可以 | 不可以 | 範圍待確認 |
| 授予／撤銷個人資料分享 | 可以 | 不可轉授權 | 提案不代為建立分享 |
| 管理使用者帳號與角色 | 不可以 | 不可以 | 可以，具體操作於 Day 2 定稿 |
| 設定 KPI 規則與預設目標 | 不可以 | 不可以 | 可以 |

分享先提案以「某使用者的全部上述業務資料」為單位，不做欄位或客戶子集選擇；授權可撤銷，不允許 B 將 A 的資料轉授權 C。管理員查閱不依賴個別分享，須在使用者介面說明此可見範圍。所有限制都必須由 Backend 驗證。

依最新 README，授權與撤銷必須留紀錄；紀錄至少包含操作者、資料擁有者、被授權者、動作及時間（欄位為實作提案）。帳號建立方式（管理員邀請或自行註冊）、停用行為、管理員角色變更限制仍待定稿。
