## 啟動 PC 預覽

在專案終端執行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\dev.ps1
```

等待終端機顯示 `Waiting on http://localhost:8081`，再開啟 http://localhost:8081 。終端機需保持開啟，按 Ctrl＋C 停止；重新開機後需重新啟動。前端通常自動更新，後端程式或 migration 修改後須重新啟動。

WSL 使用現有 Windows 環境啟動：

```bash
cd /mnt/d/insurance-crm-app
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\insurance-crm-app\scripts\dev.ps1'
```

先註冊測試帳號（姓名、Email、密碼），或使用本機 seed 帳號。需要初始化管理員時執行 `powershell -ExecutionPolicy Bypass -File .\scripts\dev.ps1 -Task db:seed`；既有帳號不重設密碼。憑證保存在 Git 忽略的 `.data/dev-accounts.txt`，不得貼入 README 或提交版本庫。

資料預設存於 `.data/development.sqlite`，可透過環境設定更改；目前沒有上傳雲端，請使用假資料測試。

其他電腦需先安裝 Node.js 24 LTS，執行 `npm ci`、`npm run dev`。詳細結構、已完成與未完成範圍見 [實作架構](docs/architecture.md)，驗證結果見 [測試紀錄](docs/testing.md)。

**錢脈**是一款以**行事曆**為核心，整合聯絡人管理、客戶追蹤、未定行程與業務計分的業務管理 App。

產品主要面向台灣業務人員，希望透過簡單直覺的操作方式，協助使用者管理人脈、安排業務行程、維持客戶聯絡頻率，並透過清楚的成果回饋，提高持續使用與完成業務目標的動力。

# 一、專案背景

業務人員在日常工作中，需要持續管理大量客戶、潛在客戶與業務行程。

常見需求包含：

* 管理聯絡人
* 記錄客戶資訊
* 管理客戶重要程度
* 維持固定聯絡頻率
* 記錄與客戶的互動
* 安排下一次聯絡
* 管理每日行程
* 保存尚未確定日期的事項
* 追蹤每日或週期性的業務目標

目前市面上已有相關業務管理工具，但部分產品功能較多、操作較複雜，並非所有功能都符合實際業務工作的需求。

因此，本專案希望建立一套：

> **簡單、快速、以行事曆與人脈管理為核心的業務管理工具。**

# 二、產品核心概念

錢脈並非單純的聯絡人 App，也不是單純的行事曆。

目前產品核心由以下主要功能組成：

```text
錢脈
│
├── 行事曆
│
├── 新增聯絡人（＋）
│
├── 聯絡人管理
│
├── 未定行程
│
└── 計分卡
```

使用者開啟 App 後，主要透過行事曆掌握每日工作，再從聯絡人、未定行程與計分系統完成日常業務管理。

# 五、App 主要架構

登入後進入「主頁／我的一天」，保留日曆與「新增聯絡人」按鈕。頂部深色成果大框改為小型狀態列，顯示今日得分、聯絡安排、已登記行動筆數與累計總分，並可進入計分卡查看成果。

主畫面底部固定為：**計分卡｜分級｜主頁｜聯絡人｜未定行程**，主頁在正中間。未定行程有未完成事項時，右上角顯示紅色數字徽章；零筆隱藏，超過 99 筆顯示 99+。

聯絡人新增／編輯是完整頁面，不是小視窗；頁內底部為 **分級｜主頁｜紀錄**，此處主頁是聯絡人基本資料。上方「儲存」才提交變更，成功後留在原頁；有未儲存修改時返回，跳出繼續編輯／放棄修改並返回的確認視窗。分頁切換保留草稿。

管理員登入後另有「管理後台」入口，一般使用者不顯示。

# 八、客戶分級

已確認預設等級與聯絡間隔：

| 等級 | 聯絡間隔 |
| --- | --- |
| A | 30 天 |
| B | 60 天 |
| C | 90 天 |
| D | 120 天 |

所有等級（含預設 A、B、C、D）皆可修改聯絡間隔，也可新增其他分級。名稱為 1–20 字元，可用 AA、VIP 或中文，首尾空白移除、英文轉大寫，不可重複；間隔可設定 1–1200 的整數，單位為天、週或月。仍被任何聯絡人使用的等級不能刪除。主頁「聯絡的節奏」依實際設定顯示。

舊版固定 A＝1 週、B＝1 個月、C＝3 個月會在讀取時轉為新版預設並補上 D；已有自訂 D 或已調整的間隔會保留。預設天數按實際日數計算；選擇月份時按日曆月計算，月底無對應日期時取該月最後一天。

# 九、聯絡頻率與安排

* 首次聯絡依建立日期（台灣時間）加上分級間隔安排；未分級不自動安排。
* 每次新增聯絡紀錄或完成聯絡，都需重新確認分級，沿用原等級也必須明確選取。未選仍可保存內容與計分，但列入「待重新分級」，不沿用舊分級安排日期。補分級後依該次聯絡日期加分級間隔安排下次。完成聯絡表單可一併選級與調整建議日期。
* 儲存時一起保存紀錄、計分與下一次安排；下次日期須晚於完成日期，也可留空進入未定清單。
* 「重新安排日期」保存原日期與新日期歷史，不新增聯絡分數。
* 「撤銷最近一次安排」按逆序恢復原日期；若撤銷的是完成聯絡，也移除該次紀錄並撤銷分數。
* 已明確安排的日期不會因分級間隔變動而自動重排；修改一般紀錄也不會重排，需使用「聯絡安排」。
* 每位聯絡人維持一個下一次聯絡安排；另可新增多筆自由行程，選填聯絡人、日期、時間、顏色與內容。聯絡人搜尋採姓名前綴比對，輸入框下方逐列顯示建議並可點選。
* 有關聯聯絡人的自由行程按「標記完成」，可一併填寫實際日期、內容、計分項目與重新分級；按「儲存完成與聯絡紀錄」一次保存。未分級列入未定；也可選「僅完成行程，不新增聯絡紀錄」。沒有聯絡人的行程只更新完成狀態。
* 行程與產生的聯絡紀錄可互相查看；恢復未完成再完成不重複建立紀錄或計分。恢復或刪除行程保留既有紀錄與分數；刪除關聯紀錄或撤銷該次聯絡安排，會撤銷分數並將仍存在的來源行程恢復未完成。
* 月曆日期格顯示各行程設定的色點，列表沿用相同顏色；完成項目保留原色並淡化、標示完成，未完成紅色數字徽章獨立顯示。

# 十、聯絡紀錄

手動紀錄欄位為 **日期、內容、計分項目（可不計分）**，日期預設台灣今天；不另要求聯絡方式、備註、下一步等欄位。

* 編輯聯絡人 → 紀錄 → 新增紀錄，填寫後按上方「儲存」才保存；分頁切換不自動儲存。
* 每筆手動紀錄可編輯與刪除，刪除需確認。聯絡人詳情也可直接查看、編輯及刪除已保存紀錄，不必進入編輯聯絡人頁。
* 詳情頁的「儲存紀錄／確認刪除」直接提交該次操作；編輯聯絡人頁內則統一由上方儲存提交。
* 建立聯絡人後，自動顯示建立日期紀錄。依目前決定保留，不提供編輯或刪除。
* 姓名、分級與其他聯絡人資料不會因修改紀錄而被自動重設。

---

# 十一、未定行程

與主頁日曆分開，包含以下部分：

1. **到期未完成月曆**：今天及過去尚未完成的聯絡安排，按原安排日期顯示紅色數字，點日期看下方列表。未來安排仍在主頁查看。
2. **尚未安排日期**：在聯絡安排中明確留空日期的聯絡人，另列清單，不放入日期格。

3. **待重新分級**：已保存新的聯絡紀錄，但尚未重新確認等級；列在未定清單並計入底部紅點，補分級後移除。歷史舊紀錄不自動追補此狀態。

底部未定徽章加總各類，每位聯絡人不重複計數。封存聯絡人不計入提醒。點項目可進入聯絡人詳情，完成聯絡、重排或撤銷；新日期保存後更新日曆與紅點。新增聯絡人未設定分級，也列入未定「尚未分級」及底部紅點；補分級後依建立日期安排首次聯絡。封存者不計入。

自由行程也納入上述日曆與通知：無日期或今天及過去未完成的行程計入紅點；完成後移除提醒。主頁保留已完成行程，可重新標為未完成。日期重排保留原始日期及變更歷史，刪除需確認。關聯聯絡人封存不會自動取消獨立行程。

# 十二、計分卡

**計分卡只能查看，不能登記、編輯或撤銷分數。** 新增聯絡人成功儲存時自動計聯繫 1 分；另外可從聯絡紀錄選項目並儲存，或完成聯絡流程一起產生計分。

## 12.1 計分規則

| 項目 | 初始分數 |
| --- | --- |
| 聯繫 | 1 |
| 接觸 | 5 |
| 活動 | 5 |
| 看店 | 8 |
| 深度面談 | 10 |
| 上卡 | 40 |

分數由後端提供，已保存項目保留當時名稱及分數。後台已提供各項分數設定表單；既有紀錄不回算，更換計分項目時套用當時規則。

* 分數無上限、跨日累積；40 是上卡單次分數，不是滿分或每日目標。
* 新增聯絡人與其聯繫 1 分在同一交易保存，失敗會一起回滾；以聯絡人 ID 防止重複計分，重試、再次儲存或編輯同一人不會再加分。既有聯絡人不追補新增分數。
* 新增聯絡人的分數固定為 1 分，不因後台聯繫分數設定改變；其他聯絡紀錄依 KPI 規則計分。
* 紀錄與計分在同一交易保存；重複儲存同一紀錄不會重複加分。
* 修改紀錄內容不重算歷史分數；修改日期會移動計分日；改計分項目依當前規則重算。
* 刪除紀錄或改為不計分會撤銷對應分數，累計排除已撤銷項目。
* 過去未選計分項目的紀錄不自動補分。

## 12.2 週報／月報

老闆在管理後台設定全站週期，預設週報（週一至週日），可改為月報（每月一日至月底）。使用者選日期後，顯示該期範圍、分數、有效行動筆數、分類統計及明細；另外保留每日得分與累計總分。

結算不歸零、不設上限。目前報表是即時統計，修改舊紀錄會更新歷史報表；鎖帳、封存報表及定時寄送尚未提供。

# 十三、成果回饋與使用動力

採用溫暖綠金配色、每日成果摘要與清楚的操作回饋，不做角色養成或遊戲系統。每日得分與跨日總分無上限，不設定 40 分滿分或達標進度。

計分卡只能查詢；新增聯絡人成功儲存自動計聯繫 1 分，聯絡紀錄則選擇計分項目並儲存後計分；刪除紀錄會撤銷該筆紀錄的分數。後台可決定週報或月報，結算不清除累計總分。

# 十四、帳號註冊與權限

註冊必填 **姓名（1–80 字元）、Email、密碼（8–128 字元）**。其他帳號個人欄位目前未增加。自行註冊是否開放由後端設定，正式環境預設關閉。

每位使用者的聯絡人、安排、紀錄與計分各自隔離。一般帳號不可直接查閱或修改他人資料，管理員與授權讀取由後端檢查權限。

**填寫 Email 不代表已完成信箱驗證。** 登入頁已提供「信箱驗證／忘記密碼」：申請／重寄驗證信（24 小時有效）、密碼重設（30 分鐘有效），一次性 token 儲存雜湊，重設後所有登入失效。正式環境強制驗證，本機預設不強制。開發信件存於 `.data/mail-outbox`，不對外寄信；已提供 Resend 轉接器，實際投遞需配置服務與網域。更換信箱及正式邀請仍未實作。詳見 [寄信與部署](docs/deployment.md)。

# 十五、資料授權

目前需求包含使用者之間的資料授權機制。

例如：

```text
使用者 A
    │
    │ 授權
    ↓
使用者 B
```

授權後：

```text
B 可以查看 A 的資料
B 不可以修改 A 的資料
後台管理帳號可以修改
```

因此權限概念至少包含：

```text
自己的資料
├── 查看
├── 新增
├── 修改
└── 刪除

被授權的其他使用者資料
├── 查看
└── 不可修改
```

已提供「授權分享」入口：輸入既有帳號 Email，確認後分享自己帳號的全部聯絡人、紀錄、行程及計分報表；可查看授權名單並撤銷。對方從「分享給我」搜尋分享者並唯讀查看，不能修改或轉授權。

撤銷後 API 立即拒絕新請求，已開啟的分享畫面每 15 秒重新檢查權限並關閉失效資料；已看過的資訊無法收回。分享者停用時也禁止讀取；恢復帳號會恢復尚未撤銷的授權。管理員既有後台權限不受分享撤銷影響。

* 可以取消授權
* 需要授權紀錄

# 十六、管理後台

老闆使用管理員帳號登入同一 App，從「管理後台」進入。

已實作：

* 帳號列表以姓名為主，附 Email 區分同名者；可用姓名或 Email 搜尋。
* 舊帳號沒有姓名時以 Email 顯示；老闆可在帳號設定補填或修改姓名。
* 點帳號進入該使用者資料頁，查看聯絡人（含封存）、搜尋聯絡人、查閱基本資料、紀錄、安排歷史及計分／週月報。
* 設定全站週報／月報，查看稽核紀錄；一般帳號不能呼叫管理 API。

* 建立帳號（姓名、Email、初始密碼及權限）、停用／恢復、調整使用者／管理員權限，提交前顯示確認。停用保留資料但立即撤銷登入；權限變更也撤銷舊登入。不可停用自己或修改自己的管理權限。
* 點入帳號可編輯既有聯絡人及其紀錄、分級，也可編輯既有自由行程。沿用儲存及未儲存提醒，資料版本衝突不覆蓋其他人的更新；不能代新增或刪除他人聯絡人與行程。
* KPI 表單逐項設定 0–10000 整數分數；既有分數保留，新增計分或更換計分項目套用目前規則。帳號、資料與規則修改都有操作紀錄。

建立帳號目前由老闆設定初始密碼；使用者可從登入頁申請信箱驗證或重設密碼，正式邀請信仍未提供。

# 十九、資料安全與隱私

錢脈預期可能處理：

* 姓名
* 電話
* Email
* 生日（及保留的舊版重要日期）
* 聯絡紀錄
* 人際關係資訊
* 客戶分類
* 行程
* 業務備註
* KPI 資訊

因此資料安全屬於核心需求。

基本原則：

* 使用者必須經過身分驗證
* 不同使用者資料必須隔離
* 資料存取必須經過權限檢查
* 被授權資料應遵守 Read-only 等權限限制
* 客戶資料不得公開存取
* 測試期間不得任意使用真實客戶資料
* 正式環境與開發環境應適當區隔
* 敏感資訊不得直接寫入程式碼
* Backend 必須實作正式授權機制

正式上線前，應另外確認台灣個人資料保護及相關法規要求。

## 23.3 每日工作方式

1. 確認當日交付物，拆成能在當天驗收的小任務。
2. 從 `develop` 建立 `feature/*` 或 `fix/*`，完成介面與資料串接。
3. 檢查正常操作、空資料、輸入錯誤、失敗提示與權限；關鍵規則補自動化測試。
4. 通過檢查後提交並整合，更新排程、阻礙與下一步。
5. 新需求先記入待辦；若納入本期，同時調整範圍或工期。

已確認採用 **PC 瀏覽器為主要確認方式；手機測試目前暫緩，先補齊 PC 功能**。技術選型必須支援 PC 預覽；手機階段檢查觸控、鍵盤、返回與版面差異，交付前完整驗證 Android 與 iOS。各功能檢查點見 [需求規格](docs/requirements.md)，第一個功能的操作情境見 [使用流程](docs/user-flow.md)。
